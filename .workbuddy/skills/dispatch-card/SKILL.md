# 派工：卡片怎么发

规则的正本在 `docs/开发架构.md` 第 10 节「怎么派工」，结构预算与合卡准入在 10.1–10.3。这一页是把它做成动作。两者不一致时以第 10 节为准，并停下来说冲突。

## 派工前先读（只读这几段）

按顺序读，读完就停，不整份翻。检索禁区、每卡文件预算、收尾用哪条 CI 都写在仓库根的 `AGENTS.md`，这里不重复：

1. `docs/任务队列.md` 顶部四个指针（`CURRENT` / `NEXT` / `STAGE` / `PLAN_GATE`）+ 这一张的行
2. `docs/开发架构.md` 第 10 节（派工规则、10.1 结构预算、10.2 合卡准入、10.3 结构体检）、第 11 节（这张卡的交付与完成标准），以及本卡在 14.x 的那一行
3. `docs/开发日志.md` 最上面一条，看上一张卡实际做到哪
4. 本卡要改的文件，按符号 grep 后读 30–60 行；当模板的上一张实现文件只看签名与关键段

`CURRENT` 不是 `—` 时说明还有卡没收口：先报告「当前 X 还在进行中，下一张是 Y」，不要开新卡。

## 随卡的文档索引，不是全文

派工正文里固定写这三行，节号要落到具体位置。**写不出节号，说明还没定位到，先 grep 再派**：

- `docs/MMO系统架构方案.html`：玩法正本。本卡读 `#{锚点}`（`#s7` 战斗 / `#s9` 装备 / `#s10` 副本 / `#s11` 社交 / `#s12` 经济 / `#s13` PVP / `#s14` 节奏投放），只读那一节
- `docs/技术架构.md`：进程边界正本。本卡读「{进程名}」那两段
- `docs/开发架构.md`：只做指定的这一张卡。读第 10 / 11 节与本卡在 14.x 的那一行

两头都不许：不许把文档缩成一句「按文档来」（等于没给正本），也不许整份投喂（每卡固定两三万输入 token，命中率不到一成）。

## 前置声明，原文照抄

把这段放在卡号前面，一字不改：

> 只实现开发架构里的这一张任务卡。不要提前做后面的卡，不要改方案里已经写定的玩法。数值还没定的地方留成配置，不要在代码里写死概率。语言、传输和存储按开发架构第 2 节，不要另起一套。做完后按这张卡的完成标准逐条说明结果。遇到规则冲突就停下来，不要自行改规则。

## 合卡与拆卡：先过判据再派

派工前若觉得这一行该并进上一行、或该再拆一次，先按 10.2 判：

- **合**：验收主体相同 / 依赖完全重合 / 回滚粒度可接受 / 合后手写业务 ≤1600 行，四条全满足才合。合完把两处完成标准抄进同一张卡，核对时逐条都过，不许只核一边
- **拆**：只认一条——跨了不同的验收主体（DB 迁移 / 协议变更 / 客户端屏幕 / 配置表）。只是「内容多、功能点密」的不拆
- 合或拆之后要同步：任务队列顶部的张数、`## 主队列（N 张）`、闸门表、README 与 `docs/未覆盖排期.md`，并在任务队列的「合卡记录」留一行写明理由（张数一共六处，漏一处就自相矛盾）
- 带 `★` 的卡、风险列非空的卡、阶段 6 的 Q31 / Q32 / Q35：**不许合**

## 结构预算（10.1）：数字现取，不抄

- **优先往既有域脚本里追加用例，不新开 `check-*.sh`**。现值跑 `bash tools/check/check-structure-budget.sh`，数字读 `tools/check/structure-baseline.txt`——**现取，别抄进文档**（抄一次就过期一次）
- 确需新开只有一种情形：**新域**（横跨多个模块，既有卡脚本都只顾自己那条路）。此时脚本 ≤350 行，先跑一遍闸门
- 能往 `lib-common.sh` 提 helper 就不新写，不许重定义 `ok` / `bad` / `expect_json` / `finish`
- 单卡新增 check ≤300 行、日志 ≤50 行；超了就是在造第二套框架，停下来合域
- 闸门红了先还结构债，再派新卡

## 卡片的形状

派出去的正文按这个顺序，缺一段就是没派完整：

1. **卡号与这一行**：编号加一句这一行要交付什么
2. **文档索引**：上面那三行，含具体节号
3. **前置声明**：上面那段引文
4. **这一行的范围**：做什么、不做什么。后面的行不提前做，前面的行不顺手改。
   若这张卡会改动已有卡依赖的事实（接一种发货、改签名 / 构造链、改配置 schema、加状态字段），
   先写清「哪几张老卡的断言会受影响、要不要重跑」，开工前在 `tools/check/` 里搜一遍写死的数字
5. **完成标准**：从第 11 节抄这张卡的完成标准，逐条可核对，不写成「代码写完」。
   每条后面补「证据」：跑什么命令、看哪一行输出；必须真服或真机的当场标出来，实现阶段顺手做，不留到收尾
6. **核对方式**：跑哪个脚本、看什么输出；有 `tools/check/check-*.sh` 的写清命令。
   日常收尾 `bash tools/check/ci.sh --changed`；改了 proto / 迁移 / 网关签名 / 公共库的一律全量 `bash tools/check/ci.sh`。
   静态断言不许写死 `delivered_kinds=数字`，也不许把「还没接发货」绑死某个商品编号（`preflight.sh` 第 4 闸会拦）；
   起服相关用 `tools/env/service-harness.sh`，坏表 / 坏清单用 `lib-common.sh` 的 helper
7. **收尾要求**：把卡号、做了什么、核对结果写进 `docs/开发日志.md` 最上面（≤50 行），不写密码和连接串；
   **当场 commit + push**（漏提交会把两张卡混进一个改动里）；
   改了 proto 或客户端 Net 层的，记一次「真机欠项」并累加，平板回来后一次性出包跑 `check-p0-3c.sh`

## 派的时候落在哪儿

- 建任务（TaskCreate）：把 1 到 7 段整段写进 description，第 2 段是索引不是「按文档来」
- 派子代理（Agent）：prompt 里同样带全 1 到 7 段，外加「先按索引读那几节再动手」
- 用户只说了卡号：先按第 14 节找到这一行，补全 1 到 7 段再开工，不要拿卡号直接开写
- 一次只派一行；派完停下等结果，不自动续下一张

## 禁止

- 一次派两行，或者把后面的行拼进这一次
- 绕开三份文档，自己另立一套玩法或进程划分
- 拿「索引式投喂」当借口不看文档，凭印象写玩法
- 在代码里写死概率、掉落、冷却数字（进 `config/`）
- 发现两份文档打架时悄悄按其中一份改掉另一份
- 卡没核对完就说完成，或者做完不提交
- 让结构预算比基线更差还往下派
