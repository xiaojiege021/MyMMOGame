# 配置设计 · 物品 / 商城 / 商店 / 生产 / NPC / 怪物

> 目标：让「具体数值、具体物品、地名、NPC」都只改 `config/` 就能增添改查；代码只读表和校验。
> 状态：设计稿（2026-11-16）。K1–K7 按这份字段与样例落，不各写一套；K5 已按第 2 节落 `item-table/3`（2026-11-17，v1.164）；K7 已收口城 / 赛季的配置与库边界（v1.165）；K6 已收口 NPC / 怪物与客户端内容表（v1.166）；K3 已按第 7 节落 `recipe-table/1`（v1.180）。
> 边界：静态定义在配置，可变状态在库，临时状态在进程内存。细节见 [技术架构 6.1](技术架构.md)。

## 1. 命名与 ID

| 类型 | 规则 | 例子 |
| --- | --- | --- |
| 物品编号 | 小写 + 下划线，全仓唯一；同一件物品只允许一个编号 | `ore_iron`、`sword_trade`、`pill_rejuvenate` |
| 商品编号 | `shop_<种类>_<序号>` | `shop_red_talisman_1` |
| NPC 编号 | `npc_<拼音>` | `npc_wen_sao` |
| 怪物编号 | `mob_<拼音>` / `boss_<拼音>` | `mob_kulan_beast` |
| 配方编号 | `recipe_<产物>` | `recipe_pill_rejuvenate` |
| 地名 | 直接用方案 2.5 的中文名；文件名即编号 | `region/枯岚道.json` |
| 对话 | 文件名即人物编号 | `dialogue/闻嫂.json` |

规则：

1. 编号一旦进库就不再改名；改中文名只改 `name`，不改 `id`。
2. 新增物品 = 加 `items.json` 一条；新增商品 = 加 `shop.json` 一条；新增 NPC = 加 `npc.json` 一条 + 可选 `npc_shop.json`；不改代码。
3. 会变的计数不进配置：`sold_today`、`bought_today`、`owner_sect`、`stock_now`、`claimed` 只在库。

## 2. items.json（v3，K5 已落地）

旧字段：`id / name / kind / stack_max / bind / weapon_kind / require_level`。
K5 已落：`grade`、`set_id`、`icon`、`desc`，全表 39 件补齐，schema 为 `item-table/3`。
**`part` 暂不写进 items.json**：装备部位仍只在 `crystal.json` 的 `equipment_parts` 一处（配置设计 9「同一个数只留一份」），
B2 / W1 要合并再改这里；`effect` 与消耗品数值归 B1。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 唯一编号 |
| `name` | 是 | 中文名 |
| `kind` | 是 | `material` / `consumable` / `equipment` / `crystal` / `voucher` / `title` / `appearance` / `home_decor` / `tool` / `bag` |
| `grade` | 否 | `white` / `green` / `blue` / `purple` / `orange` / `red`；装备必填，材料 / 结晶等可空 |
| `set_id` | 否 | 套装编号，`set_<小写编号>`；空串表示不属套装。B2 起按 `sets.json` 填，件数与加成也在那份表 |
| `part` | — | 暂不写入；部位在 `crystal.json` 的 `equipment_parts` 一处 |
| `weapon_kind` | 否 | `staff` / `spirit_sword` / `saber` / `spear` / `mace` / `axe` / `bow` / `crossbow` |
| `require_level` | 否 | 穿戴等级 |
| `stack_max` | 是 | 堆叠上限，装备为 1 |
| `bind` | 是 | `none` / `on_pickup` / `always` |
| `icon` | 是 | 图标地址，当前统一写 `icon/<物品编号>` 作占位 |
| `desc` | 是 | 说明文字，不许空串 |
| `effect` | 否 | 只有消耗品用；见下 |

消耗品 `effect` 的通用形状：

```json
{
  "type": "heal_hp_pct",
  "value": 30,
  "cooldown_group": "red",
  "cooldown_s": 30
}
```

`type` 先支持：`heal_hp_pct`、`heal_mp_pct`、`heal_hp_over_time`、`heal_mp_over_time`、`breakthrough_bonus`、`buff`。新增类型要改代码；新增同类型物品只改配置。

样例：

```json
{
  "id": "sword_trade",
  "name": "行商长刀",
  "kind": "equipment",
  "grade": "green",
  "set_id": "",
  "weapon_kind": "saber",
  "require_level": 15,
  "stack_max": 1,
  "bind": "none",
  "icon": "icon/sword_trade",
  "desc": "行商带来的长刀。"
}
```

```json
{
  "id": "pill_rejuvenate",
  "name": "回春丹",
  "kind": "consumable",
  "grade": "white",
  "set_id": "",
  "stack_max": 99,
  "bind": "none",
  "icon": "icon/pill_rejuvenate",
  "desc": "立即回复一部分生命。",
  "effect": {
    "type": "heal_hp_pct",
    "value": 30,
    "cooldown_group": "red",
    "cooldown_s": 30
  }
}
```

> 上一条的 `effect` 是 B1 的目标形状，当前 `items.json` 的丹药还没有 `effect` 与数值（归 B1）。

K5 的加载期校验（`ItemTable.Load`）：grade 只认六档且装备必填；`set_id` 只能出现在装备上且形状为 `set_<小写编号>`；
`icon` 必须是 `icon/` 开头的地址；`desc` 不许空。坏一处就 `config_error`，不静默落空串。
四个字段的只读出口是 probe 的 `--item-list`（与真实启动共用同一个 `ItemTable.Load`）。

## 3. shop.json / home_coin_shop.json（目标 v11 / v2）

一条商品 = 一个 `id` + 一个 `delivery`。价格只在商品表，不写进 `items.json`。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 商品编号 |
| `name` | 是 | 商品名 |
| `category` | 是 | 18 类之一；只作展示分组 |
| `price` | 是 | 正整数；0 表示免费 |
| `currency` | 是 | `yuanbao` / `home_coin` / `gold`；必须在 `currency.json` |
| `delivery` | 是 | 发货方式，见下 |
| `limit` | 否 | `per_character` / `per_day`，0 = 不限 |
| `stock` | 否 | `rule`: `unlimited` / `daily` / `weekly`；配 `count`；**当前余量在库** |
| `on_sale` | 否 | 是否上架；缺省 true |
| `note` | 否 | 说明 |

`delivery.mode`：

| mode | 需要字段 | 行为 |
| --- | --- | --- |
| `item` | `item_id`、`count` | 进背包；走 `ApplyGrant` 同一事务 |
| `wardrobe` | `item_id` | 进外观收藏；不占背包格（B7+B8 接发货时定） |
| `bag_slots` | `count` | 角色背包上限 +N |
| `guild_display` | `display_id` | 宗门展示解锁 |
| `season_pass` | `pass_id` | 开付费轨 |
| `monthly_bundle` | `bundle_id` | 月叠一次性到账 |
| `second_slot` | 无 | 账号角色位 +1 |
| `none` | 无 | 未接发货；购买回 `delivery_pending`，不扣钱 |

样例：

```json
{
  "id": "shop_red_talisman_1",
  "name": "红符",
  "category": "red_talisman",
  "price": 15,
  "currency": "yuanbao",
  "delivery": { "mode": "item", "item_id": "talisman_red", "count": 1 },
  "limit": { "per_character": 0, "per_day": 0 },
  "stock": { "rule": "unlimited" },
  "on_sale": true,
  "note": "到账即绑，只回复自己。"
}
```

```json
{
  "id": "shop_season_pass_1",
  "name": "赛季通行证",
  "category": "season_pass",
  "price": 700,
  "currency": "yuanbao",
  "delivery": { "mode": "season_pass", "pass_id": "current" },
  "limit": { "per_character": 1, "per_day": 0 },
  "on_sale": true,
  "note": "状态发货，不背包。"
}
```

迁移期：旧的 `delivery_item_id` / `delivery_count` 保留为兼容字段；K1 收口后删除。

K6 落地（v1.166）：`config/npc.json` 有 **11 位**——九位开口的人各一条，外加 `npc_shop_qiyun` / `npc_shop_sect` 两位商店执事（`shop_id` 指向 `npc_shop.json`）。

## 7. recipes.json（v4，B3 已落地）

> K3（v1.180）落 `recipe-table/1`：四个副职按方案 12 章「炼丹 → 铁匠 → 裁缝 → 巧匠」，
> 8 条配方是占位（整表 `pending=true`）。方案只写定「药给炼丹、矿给铁匠」，
> 没给裁缝 / 巧匠的材料来源与任何具体配方，B1 / B3 再定真实内容；改一条配方只改这份文件。
>
> `unlock_level` 在 K3 是**角色等级**（1–100）。B3 也不引入副职等级：熟练度只用
> `character_profession.craft_count` 这个计数器选权重档，这一格的含义没变。
> 版本脉络：K3 v1（8 条占位）→ B1 v2（炼丹六条真实配方）→ B2 v3（产出装备必写 `grade`）
> → B3 v4（产装备的四条写 `grade_roll`，掷点区间与权重在 `craft_roll.json`）。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 固定 `recipe-table/1` |
| `version` | 是 | 1；改一次表加一次 |
| `pending` | 否 | 整表还是占位；与数值台账表 B 的集合对应 |
| `professions` | 是 | 四个副职，**编号与顺序**必须是 `alchemy` / `blacksmith` / `tailor` / `jeweler`；`name` 只查非空与不重复 |
| `recipes[].id` | 是 | `recipe_<小写编号>`，全表唯一 |
| `recipes[].profession` | 是 | 必须在 `professions[].id` 里；每个副职至少要有一条配方 |
| `recipes[].unlock_level` | 是 | 角色等级 1–100（K3 口径；B3 接副职等级时另加字段） |
| `recipes[].inputs` | 是 | `[{item_id, count}]`；物品必须在 `items.json`，同一配方不重复，`count ≥ 1` |
| `recipes[].fee` | 否 | `{币种: 数量}`；币种必须在 `currency.json`，数量非负；`0` 等于不收这一种 |
| `recipes[].output` | 是 | `{item_id, count}`；物品必须存在，`1 ≤ count ≤ stack_max`（一次入包，不拆格） |
| `recipes[].success_pct` | 是 | 0–100；只在角色服 `finish` 那一手掷一次 |
| `recipes[].craft_time_s` | 是 | 0–86400；`start` 写 `ready_at = now() + craft_time_s`，到点前 `finish` 只能被拒 |
| `recipes[].grade_roll` | — | 产装备的配方**必填**，非装备**不许写**（B3）：`{attr_min, attr_max, extras_max}`，三个数缺一个就 `config_error`；区间与品阶基准的对账在 `CraftRollTable.CheckRecipes` |
| `recipes[].note` | 否 | 说明；不参与加载 |

```json
{
  "id": "recipe_pill_rejuvenate",
  "profession": "alchemy",
  "unlock_level": 1,
  "inputs": [{ "item_id": "herb_ling", "count": 2 }],
  "fee": { "gold": 10 },
  "output": { "item_id": "pill_rejuvenate", "count": 1 },
  "success_pct": 100,
  "craft_time_s": 5,
  "note": "最基础的回复丹。药材与成功率是 K3 占位，B1 定真实数值。"
}
```

**制作掷点（B3，方案 9.1）**：`config/craft_roll.json` 是掷点的唯一正本（`craft-roll/1`，整表 `pending=true`）。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `skill_tiers[].min_crafts` | 是 | 该副职累计制作次数下限；第一档必须是 0，严格递增 |
| `skill_tiers[].high_weight` | 是 | 1–100；只把中段与高段的权重乘上去，不抬区间上限、不改品阶 |
| `extra_count_max` | 是 | 1–2（方案「最多两条附加属性」） |
| `extras[]` | 是 | `{slot, grade, attr, min, max}`；必须覆盖 `items.json` 里现取的全部装备「部位 × 品阶」，同组不重复；`attr` 当前只有 `attack` |

掷点落库：`inventory.craft_attr`（主属性）+ `inventory.craft_extras`（`jsonb`，`[{attr,value}]`），
两列同生同灭（`inventory_craft_roll_paired`）；非制作产出的两列都是 `NULL`，攻击仍按 `items.json` 算。
熟练度落 `character_profession`（角色 × 副职 → `craft_count` / `success_count`），只增不减。
`EquipRepository.WornTotals` 读 `coalesce(craft_attr + 附加 attack, items.attack)`，所以强化按掷出来的基础算。
只读入口：`--craft-roll-sample <recipe_id> <n> <craft_count>`（纯函数抽样，不起服、不连库）。

**制作分两笔事务**（`CraftRepository`）：

1. `start`：抢事务号 → 锁角色行读等级 → 扣材料 → 扣费用 → 检查产出放得下 → 写 `craft_job`。
   材料 / 费用 / 活同一条事务；任何一项不满足整笔回滚，拒绝时数值一个字节不动。
2. `finish`：抢事务号 → 锁 `craft_job` → 没过 `ready_at` 拒 → 掷 `success_pct` → 成功才入包 →
   写 `craft_log` 结果 → 删 `craft_job`。失败也记流水，但不返材料、不给产出。

成功率与耗时只从这份文件读，代码里不写第二套；库里只存「哪条配方、成没成、产出什么」，
不存材料 / 费用 / 概率 / 时长的副本。产出入包复用 `GrantRepository.ApplyItemDeltasInTransactionAsync`，
费用扣减复用同类的 `ApplyCurrencyDeltaInTransactionAsync`。

**加载期硬校验**（`RecipeTable.Load`）：schema / 版本；四个副职的编号与顺序、名字非空且不重复；
配方编号形状与唯一；每个副职至少一条；`inputs` 里的物品存在、件数 ≥1、不重复；`fee` 币种存在、
数量非负；`output` 物品存在、件数 1 到堆叠上限；`success_pct` 0–100；`craft_time_s` 0–86400；
`grade_roll` 对产装备必填、对非装备不许写。坏一处 `config_error`，不带着半截配置跑。

**只读入口**（纯计算，不起服、不连库）：

```bash
dotnet tools/probe/CliProbe/bin/Release/net10.0/CliProbe.dll --recipe-list
```

打一行表头（版本 / 是否整表占位 / 副职数 / 配方数）、每派一行（编号 / 名字 / 条数）、
每条配方一行（编号 / 副职 / 解锁 / 材料 / 费用 / 产出 / 成功率 / 耗时）。
另加 `--recipe-table-path <临时表>` 可指到仓库外的一份做坏配置核对，不影响启动。

## 8. 地名与对话（沿用现有）

- 地名：`config/region/<地名>.json`，字段 `id / name / chapters / neighbors / faction / open / note`。新增地名 = 加一个文件。
- 对话：`config/dialogue/<人名>.json`，NPC 的 `dialogue_id` 指向它。新增台词 = 加一条，不改代码。客户端 `UiContentTable.SpeakerDialogue` 由 `tools/gen/gen-ui-content.py` 逐条生成（C5），手写客户端只读生成表，不再抄第二份。
- 势力：`config/world.json` 的 `factions`，与 `mainline.json` 的 `factions` 保持一致。

## 9. 配置与库的边界（摘录）

| 放配置 | 放库 |
| --- | --- |
| 物品定义、价格、商品、配方、NPC、怪物、地名、对话、掉落、奖励、概率、次数、时间、限购规则 | 角色、背包实例、货币、强化等级、任务进度、宗门成员、挂单与成交、洞府摆放、城池归属、库存计数、赛季领取 |

同一个数只留一份：

- 日限购 5 是配置；今天买了几件是库。
- 配方成功率 70% 是配置；这次成没成写流水。
- 物品基础价在商店表；玩家成交价在交易表。
- 强化上限 +12 是配置；每件装备当前等级在库。
- 城池归属 / 税率在库：`city.json` 只留 `city_id` / `name` / `vein_id`；「社交」.city 的 `owner_sect` 默认 `null`、`tax_pct` 默认 `0`，城战只写库，不回写配置。
- 赛季当前季 `season.current` 是配置里的运营开关；玩家领到哪一阶写库。

## 10. 校验规则

加载期硬校验，坏配置直接 `config_error` 起不来：

1. 同一文件内 `id` 唯一；文件名与 `id` 一致（地名、对话）。
2. 所有 `item_id` 引用必须存在于 `items.json`；`dungeon_drops` / `mainline_drops` / `season_pass` / `monthly_bundle` 同样。
3. `price` / `count` / `stock_per_day` / `limit` 必须是非负整数；`success_pct` 0–100。
4. `currency` 必须在 `currency.json`；`region` 必须在 `region/*.json`；`dialogue_id` 必须存在；`shop_id` 必须存在。
5. `delivery.mode=item` 必须有 `item_id` 且存在；`none` 必须没有发货物。
6. 配置里不允许出现 `owner_sect` / `tax_pct` / `sold_today` / `stock_now` / `bought_today` / `claimed` / `current_owner` 这类运行期字段；`city.json` 见到 `owner_sect` / `tax_pct` 直接 `config_error`（`siege_territory.json` 的 `tax_pct_on_capture` 是规则，不在黑名单里）。
7. `schema` / `version` 必须匹配；新增字段只追加，不改旧字段含义。
8. `items.json` 的 `grade` 只认六档；装备必须写 `grade`，其余种类可空。
9. `set_id` 只能写在装备上，形状 `set_<小写字母 / 数字 / 下划线>`；空串表示不属套装。
10. `icon` 必须是 `icon/` 开头的地址，`desc` 不许空；每件物品都要有这两个字段。
11. `npc.json` 的 `id` 形状 `npc_<小写编号>`；`region` / `faction` / `dialogue_id` / `shop_id` 必须存在；九位开口人都有 NPC，每块地表至少一位 NPC。
12. `monsters.json` 的 `id` 形状 `mob_` / `boss_<小写编号>`；`tier` 四档；`skills` 在 `skills.json`、`drops.item_id` 在 `items.json`、`spawn.region` 在 `region/*.json`；普通 / 精英怪必须有 `spawn`，`respawn_s` 1–86400。
13. 客户端人名 / 地名 / 台词只由 `tools/gen/gen-ui-content.py` 从 `config/` 生成到 `UiContentTable.cs`（含 `SpeakerDialogue` 十四条定词），手写代码不许再写 `Name = "某人"` / `Id = "某地"` / 任何一条定词；生成物与配置逐字比对，正本只有 `config/`。
14. `mainline.json` 的 `places` / `factions` / `speakers` 与同目录 `world.json` 的 `regions` / `factions` / `speakers` 逐项一致。
15. `recipes.json` 的四个副职编号与顺序、每条配方的材料 / 产出 / 费用 / 成功率 / 耗时 / 解锁按第 7 节校验；`grade_roll` 产装备必填、非装备不许写，区间按第 7 节与 `craft_roll.json` 对账。

## 12. skills.json（v3，S1 已落地）

> 这一节是 S1 补的：K0 当时没覆盖技能表，技能名与「门派 / 分支」的归属此前只活在台词里（《跑偏与缺失核对表》A10）。
> 技能表仍是**唯一正本**：名字、门派、阶、分支都在这里，代码、proto、库不写第二份。

方案出处：**2.1** 承露门是凡间门派，只教低阶技能，总称**天地玄黄**；**2.3** 立仙进明霄圣地、立魔进焦原，两处高阶技能同为**法则神通**，谁也不比谁多；**8.3** 15 级一转在承露门定分支，分支只定职责与技能差异，兵器按职业。

### 12.1 顶层

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 固定 `skill-table/3` |
| `version` | 是 | 3；改一次表加一次 |
| `note` | 否 | 口径说明，不参与加载 |
| `schools` | 否 | 门派段。**写了就逐条强校验**；不写（老临时表）退回「技能只按职业」的老口径 |
| `skills` | 是 | 技能数组，编号全表唯一 |

### 12.2 `schools[]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 小写字母开头，只含小写字母 / 数字 / 下划线 |

### 12.3 `skills[]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 技能编号，**一个都不许动**：`monsters.json`、`arena_match`、各核对临时配置都按编号引用 |
| `name` | 是 | 技能名，全表唯一；界面上的按钮文字就是它 |
| `class_id` | 是 | `tank` / `warrior` / `archer` / `mage` / `priest`；跨职业发技能按未知技能拒 |
| `school` | 有门派段时必填 | 门派编号，必须在 `schools[].id` 里 |

| `branch` | 否 | 分支编号，必须在 `branches.json` 且 `class_id` 与技能一致；**空串＝门派通用**（五条普攻） |

| `foreswing_ms` | 是 | 前摇，必须 > 0（打断要窗口） |
| `recovery_ms` | 是 | 后摇 |
| `cooldown_ms` | 是 | 冷却 |
| `stagger_ms` | 是 | 硬直 |

### 12.4 口径（别写反）

1. **`branch` 只是归属标注**：战斗服仍按 `class_id` 下发这个职业的三个技能，不按分支过滤；一转前后的可用技能集合本卡不改。
2. **门派与阶只在这里**：代码只查「命中配置里列的 id」，不写死 `tiandi` / `faze` / 十位分支 id / 任何技能名。
3. **分支职业必须一致**：`branch` 的 `class_id` 与技能的 `class_id` 不同就 `config_error`；交叉校验同时落在 `check-s1.sh`。
4. **老表兼容**：没有 `schools` 段的 `skill-table/2` 临时表（P0-3a 等老卡自带）照常加载，不校验门派与阶。
5. **名字换一次只改配置**：改完跑 `--skill-list` 就看见新名，客户端按钮文字跟着回包走，不用动客户端。

### 12.5 只读入口

```bash

```

打三样：表头（版本 / 条数 / 门派数）、每派一行（名字 / 传授方 / 阶 / 技能数 / 挂到的分支）、每条技能一行（编号 / 名字 / 职业 / 门派 / 阶 / 分支），最后一行 `skill_branch_total=<分支数> common=<通用条数>`。纯计算，不起服不连库。

## 13. effects.json（Q1 设计，待 Q2 读取）

### 13.1 顶层

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 固定 `effect-table/2`；Q1 从 `effect-table/1` 升上来，旧 `1` 不再认 |

### 13.2 `effects[]`

### 13.5 校验规则（Q2 已落地，全部报 `config_error`）

1. `schema` / `version` 不对、`effects` 为空、`id` 重复 → 起不来。
2. `kind` 不在七类里、`control` 不在 `control_types` 里、`stack_rule` 不在三种里 → 起不来。
3. `hot` / `dot` 缺 `tick_ms` 或 `tick_ms <= 0`、`shield` / `hot` 缺 `amount_pct_max_hp` → 起不来。
4. `damage.stages` 不是四条或顺序不是 `base/enhance/skill/final` → 起不来。
5. `penetration` / `resistance` 的 `cap_pct` 超 0–100、`default_pct` 为负 → 起不来。
6. `boundaries.battlefield` 里出现第二份 1.3（数字或 `ratio`）→ 起不来；只许引用 `config/battlefield.json`。
7. `effects[].pending=true` 与[数值台账](数值台账.md) 表 B 不一致 → 核对脚本红。
8. 强化段的 `结晶固定值 / 基础攻击`：`基础攻击 <= 0` 时整项按 0，Q2 不给除零异常。

### 13.6 口径

- **Q1 只写设计与配置**：`src/` 不出现 `effect-table` / `effects.json` 读取方；Q2 才接。
- **数值只有一份**：1.3 只在 `battlefield.json`，科技只在城战科技表，`effects.json` 只引用来源。
- **穿透 / 抗性已打开但默认 0**：默认值下第 4 段与方案 7.2 逐字等价；打开的是结构，不是数值。
- **效果表不管来源**：谁施加写在 `skills.json` / `items.json` 的 `effect` 块（B1 / B15）。

### 13.7 只读入口（Q2 已建）

```bash
dotnet src/Battle/bin/Release/net10.0/Battle.dll --effect-list --config config/battle.json
dotnet src/Battle/bin/Release/net10.0/Battle.dll --damage-preview --config config/battle.json \
  --attack 200 --multiplier 0.6 --defense 0 --realm-bps 0 --penetration 0 --resistance 0 --random-pct 100
```

两者都只读、不连库、不起服，与真实启动共用同一个 `EffectTable.Load` / `BattleConfig.Load`；`--effect-table-path` 可以临时换一份表做坏表核对，`--damage-preview` 的 `--random-pct 100` 用来把随机段固定成可复现的数。

### 13.8 技能 / 道具的 `effects` 块（Q2 读通，B1 / B15 填内容）

效果表只定义「是什么」，来源写在内容表里：

```json
"effects": [
  {"effect_id": "dot_poison_1", "target": "target", "stacks": 1}
]
```

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `effect_id` | 是 | 必须在 `config/effects.json` 的 `effects[].id` 里；不在就 `config_error` |
| `target` | 否 | `self`（施法者自己）或 `target`（这一手本来选中的单位：Boss 或队友），默认 `target` |
| `stacks` | 否 | 施加层数，默认 1；夹在效果的 `max_stacks` 里 |

- Q2 只把 `skills.json` 的这一段读通并接到 `StatusSet.Apply`；`items.json` 的同类块等 B1 接丹药 / 道具时用同一个入口，不另起一套计时。
- 技能里写了 `effects` 却没有 `effect_table`，按配置错起不来（不静默丢效果）。

## 14. calendar.json（Q3 已落地，v2）

日、周、赛季重置与展示时区的唯一正本。角色服、网关、全局服读同一份；世界 Boss 的窗口时刻仍由
`world_boss.json` 的窗口时刻按这里的 `timezone` 解释（Q11 起：表里写本地时刻，服务端折成 UTC 判定，改时区后出现时刻整体平移）；「显示成几点」也只从这里的时区算。

| 键 | 现值 | 说明 |
| --- | --- | --- |
| `schema` / `version` | `calendar/2` / `2` | v1 的 `season.start` 带偏移；v2 改成 `start_date`，边界跟着日重置小时走 |
| `timezone` | `Asia/Shanghai` | IANA 时区；找不到就 `config_error`，不用系统默认时区兜底 |
| `daily_reset_hour` | `5` | 业务日界线；本地 05:00 前仍算前一天 |
| `weekly_reset.day` | `monday` | 周首星期，只认 `sunday`–`saturday` |
| `weekly_reset.hour` | `5` | 周界线；与日界分开配 |
| `season.start_date` | `2026-01-05` | 第 0 段赛季的本地日期，时刻取 `daily_reset_hour` |
| `season.length_days` | `90` | 每段天数，1–365 |

### 14.1 口径

- **只有一份时钟**：服务端源码不出现数据库当天日期 / 周首函数；角色服把 `CalendarTable.DayKey` /
  `WeekStartDate` / `WeekStartInstant` 算出的日期当 SQL 参数带入，比较与写入在同一条事务里用同一个值。
- **改配置重启生效**：改 `timezone` / `daily_reset_hour` / `weekly_reset` / `season` 后，疲劳日界、
  周份额、高难本次数、赛季边界与世界 Boss 展示时间一起变；不写库、不迁移。
- **赛季边界**：`season.start_date` 当天 `daily_reset_hour` 起算，每 `length_days` 天一段；
  全局服启动日志与网关 `/season/current` 的 `season_*` 字段都从这一份算，当前是哪一季仍归全局服务。
- **世界 Boss 展示**：网关 `/world/worldboss` 的 `display_timezone` / `starts_at_local` /
  `ends_at_local` / `next_starts_at_local` 只由这里格式化；`*_ms` 仍是服务端事实值。
- **不做**：不改世界 Boss 的 UTC 窗口判定（Q11 做分线与本地显示）、不新增库表、不动 proto。

### 14.2 校验规则（Q3 已落地，全部报 `config_error`）

1. `schema` 不是 `calendar/2`、`version < 1`、顶层出现不认识的键 → 起不来。
2. `timezone` 取不到 IANA 时区、`daily_reset_hour` / `weekly_reset.hour` 不在 0–23 → 起不来。
3. `weekly_reset.day` 不是 `sunday`–`saturday`、`season.start_date` 不是 `yyyy-MM-dd` → 起不来。
4. `season.length_days` 不在 1–365 → 起不来。

### 14.3 只读入口（Q3 已建）

```bash

dotnet tools/probe/CliProbe/bin/Release/net10.0/CliProbe.dll --calendar \
  --calendar-path /tmp/calendar-ny.json --at 2026-11-18T03:00:00Z
```

只读、不连库、不起服，与真实启动共用同一个 `CalendarTable.Load`；`--at` 可给 ISO 8601 或毫秒时间戳，
`--calendar-path` 用来临时换一份时区 / 重置小时做核对。

## 15. sect_tasks.json（Q4 已落地，v2）

宗门日常 / 周常、次数与奖励的唯一正本（方案 11.1「建设和贡献来自宗门秘境和宗门任务，不从商城买」）。
Q4/J1 接入：社交服按这份表发贡献与建设，网关只转发，客户端一个数都不能带。

**次数在本表，重置边界不在本表**：日常按 `config/calendar.json` 的业务日、周常按业务周首，
两处都由 Q3 的 `CalendarTable` 算；改时区 / 改重置小时重启社交服，任务周期跟着变。
本表不另存小时数，代码里也不出现第二套日期函数。

### 15.1 顶层

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 固定 `sect-task-table/1` |
| `version` | 是 | 内容版本；Q4 接入时为 `2`（键名与 schema 未变） |
| `pending` | 是 | 数值方案没给，整份仍标待定；与[数值台账](数值台账.md) 表 B 双向核对 |
| `note` | 是 | 写明来源只有宗门秘境 / 宗门任务、不从商城买、周期键只认日历、同一笔事务 |
| `tasks[]` | 是 | 至少一条；见 15.2 |

### 15.2 `tasks[]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` / `name` | 是 | 编号全表唯一（`[a-z0-9_]`，≤64）；名字只作展示 |
| `period` | 是 | `daily` / `weekly`；周期键日常 = 业务日、周常 = 业务周首 |
| `max_per_period` | 是 | 每个周期能交几次，1–100 |
| `require_level` | 是 | **角色等级**门槛（不是宗门等级）；数量由社交服向角色服只读战斗快照判定 |
| `rewards.contribution` | 是 | 个人在该宗门的累计贡献，非负整数 |
| `rewards.construction` | 是 | 宗门建设，非负整数；与贡献不能同时为 0 |
| `pending` | 否 | 数值待定标记 |

### 15.3 运行时口径

- **同一笔事务**：完成一笔在社交库一笔事务里写进度 +1、插流水、加个人贡献、加宗门建设；
  任何一步失败整笔回滚，不会出现「次数加了、建设没加」。
- **次数与重置**：`max_per_period` 在配置；进度行的 `period_key` 由日历算，换周期就是换键，
  不需要清库或定时任务，旧周期的流水不删。
- **贡献与建设**：贡献按（宗门, 角色）累计，退出再入不迁移；建设只记在 `"社交".sect.construction`，
  只由掌门用已有升级入口消耗（P2-1a4），任务只加不减。
- **商城买不到**：商城清单、物品表、商城加载器都不出现建设 / 贡献类；清单外编号回 `not_in_list`。
- **幂等**：完成请求的 `txn_id` 由网关服务端生成，`sect_task_ledger.txn_id` 主键挡重放；
  同一号重放回 `duplicate`，不二次计次、不二次加建设。
- **等级门槛**：社交服向角色服 `DescribeBattleProfile` 只读取 `level`；角色不存在回
  `character_not_found`，角色服不可用回 `character_unavailable`，不拿配置兜底。

### 15.4 校验规则（Q4 已落地，全部报 `config_error`）

1. `schema` 不是 `sect-task-table/1`、`version < 1`、`tasks` 为空 → 起不来。
2. 任务 `id` 重复 / 为空 / 含空格或 `/`、缺 `name` → 起不来。
3. `period` 不是 `daily` / `weekly`、`max_per_period` 不在 1–100 → 起不来。
4. `require_level` 不在 1–1000、奖励为负、贡献与建设同时为 0 → 起不来。
5. 顶层或任务里出现不认识的键（比如把奖励写进 `rewards` 以外的段）→ 起不来。
6. 配置里出现「商城可买建设 / 贡献」一类反口径 → 起不来。
7. 日历表缺失 / 时区非法 / 重置小时越界 → 社交服起不来（与 Q3 同一份硬校验）。

## 16. grades.json / sets.json（B2 已落地）

两张都是 14.5 第 6 行（装备品阶与套装）的正本，只被角色服读；战斗服不读，快照里的 `equip_attack` 已含套装加成。

### 16.1 grades.json（`grade-table/1`）

```json
{ "schema": "grade-table/1", "version": 1, "grades": [
  { "id": "white", "order": 1, "require_level": 10, "base_attack": 20 }
] }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 只认 `white` / `green` / `blue` / `purple` / `orange` / `red` 六档，正好六条 |
| `order` | 是 | 1–6，连续不重复；数组顺序不参与判定，按 `order` 排 |
| `require_level` | 是 | 该档等级带的上限；装备自己的 `require_level` 不得超过它 |
| `base_attack` | 是 | 该档攻击基准，同时是全表该档装备 `attack` 的上限 |

口径：

1. 六档顺序是方案 `#s8` 写定的，代码里是枚举，不是可调数值；
2. 基准攻击与等级带方案没给，是待定值，只在这份表记一次；
3. 每档的套数不在这里写——它由 `sets.json` 与 `items.json` 对账，核对脚本按方案「3–4 套」的区间核。

校验（全部 `config_error`）：六档不齐 / 编号不认识 / `order` 不连续 / 等级带或基准不随品阶严格递增；
装备的品阶不在表里、`attack` 超过本档基准、`require_level` 超过本档等级带。

### 16.2 sets.json（`set-bonus/1`）

```json
{ "schema": "set-bonus/1", "version": 1, "sets": [
  { "id": "set_white_melee", "name": "初锋·力", "grade": "white",
    "bonuses": [ { "pieces": 2, "attack": 2 }, { "pieces": 3, "attack": 5 } ] }
] }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | `set_<小写编号>`，与 `items.json` 的 `set_id` 一一对应 |
| `name` | 是 | 套装名（中文），只做展示 |
| `grade` | 是 | 同套所有装备必须是这一档，混档起不来 |
| `bonuses[].pieces` | 是 | 生效门槛，按件数严格递增；不得超过该套在 `items.json` 里的实际件数 |
| `bonuses[].attack` | 是 | 达到该件数时加的攻击，取已穿件数能达到的最高一档 |

口径：

1. 套装只加基础属性（核对表默认值表），现有装备的基础属性只有 `attack`；
2. 效果永远按「现在穿着几件」现算，不落库、不记历史；脱下立刻回落，换装不继承（方案 `#s8`）；
3. 件数取自 `items.json` 同 `set_id` 的装备，本表不另记一份；加成数值是待定值（按该档基准的 10% / 25% 暂取）。

校验（全部 `config_error`）：编号形状不对 / 重复 / 缺 `name` / 品阶不在品阶表 /
`bonuses` 为空或门槛不递增或数值非正 / 门槛超过实际件数 / 同套混品阶 /
`items.json` 有 `set_id` 但本表没有定义（反向也拒）。

### 16.3 只读入口

```bash
dotnet tools/probe/CliProbe/bin/Release/net10.0/CliProbe.dll --grade-list
dotnet tools/probe/CliProbe/bin/Release/net10.0/CliProbe.dll --set-list
dotnet tools/probe/CliProbe/bin/Release/net10.0/CliProbe.dll --set-bonus set_white_melee 2
```

前两条不连库，走与起服同一个加载链；第三条只算「穿到几件加多少」，给核对验门槛用。
