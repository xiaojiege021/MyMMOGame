# 卡片契约

> 用途：任务队列里风险标记不是 `—` 的卡，派工时填一页，贴进《开发日志》这张卡的条目。它只回答三件事：**这张卡允许动什么、绝对不许动什么、拿什么证据收口。**
>
> 依据：[开发架构](开发架构.md) 14.10（四类不可逆点）与 14.11（风险标记与语义证据）；四类的判据、三问与锚点见 [不可逆点清单](不可逆点清单.md)。本页是模板与示例，不是玩法文档。

## 为什么要有这一页

AI 最容易出错的地方不是「不会写」，是**在相邻逻辑里顺手改**：为了修采集，改了一个判断条件；为了加字段，动了已有 RPC 的拒绝码；为了省事，把两份数值合并成一份。编译会过，静态断言也会过，因为断言只证明「名字还在」。

合同的作用是把「不许动」写在开工之前。允许改的部分写错了，CI 会红；冻结的部分被改，往往要到真机或线上才发现。所以冻结面比允许面重要。

## 模板

```text
卡号：
风险标记：            # 1/2/3/4，可组合；见任务队列的风险列
本卡只做：
不做：
允许改：              # 文件 / 目录，尽量具体
冻结（一项都不许动）：
  - proto：           # 字段编号、类型、消息名
  - RPC / 拒绝码：    # 已有 RPC 名、ok=false 的 reason、HTTP 状态
  - DB 列 / 约束 / 迁移版本：  # 已有列、CHECK / UNIQUE 名、版本号只追加
  - config 键 / schema：# 已有键名、schema 版本
  - 网关路径：        # 已有路由与回包字段
状态与拒绝码：        # 状态怎么变；每个拒绝回什么；拒绝时哪些值必须是 0
不变量：              # 引用不变量清单的编号，或写清「本卡没有新不变量」
证据：
  - 静态：            # 跑哪条 check
  - 真库 / 真机：     # 哪个库、哪台设备、哪个场景
  - 变异：            # 改坏哪一处、期望哪条断言抓住
回滚点：              # 迁移版本 / 配置开关 / 进程重启，不写「回滚代码」
```

## 示例 1：D8（第 1 类，schema 与迁移）

```text
卡号：D8
风险标记：1
本卡只做：迁移清单、schema_version、主迁移补全量、一条命令建库。
不做：不改任何表与约束的语义；不新增 CHECK；不动 proto 与客户端；不改 --migrate --sql 的老路径。
允许改：db/migrations.json、db/*/*.sql、tools/probe/CliProbe/Migration*.cs、tools/env/db-migrate.sh、tools/check/check-d8.sh、相关文档。
冻结：
  - proto：无
  - RPC / 拒绝码：无
  - DB 列 / 约束 / 迁移版本：已有 35 份 SQL 的语义只追加不改；35 个版本号只追加不插入；schema_version 的列名不改。
  - config 键 / schema：无
  - 网关路径：无
状态与拒绝码：migrate=ok；清单坏 / 空库缺 schema 报 config_error 退出 2；版本漂移报 migrate_error=drift 退出 6；SQL 失败整条回滚，版本表不留半条。
不变量：版本行数 = 清单条数；第二次跑 applied=0；空库与老库都建齐同一套表。
证据：
  - 静态：bash tools/check/check-d8.sh（无库 30 项）
  - 真库：ubu 临时库 mmo_d8_new 69/69、mmo_d8_old 67/67；information_schema 44 张数据表逐名一致
  - 变异：bash tools/check/mutate.sh --card d8（版本号跳号 / 丢 reapply 两条都被抓）
回滚点：临时库删掉即可；版本表可重建；主迁移幂等，重复跑只 skip。
```

## 示例 2：P1-5a（第 2/3 类，钱与拒绝码）

```text
卡号：P1-5a
风险标记：2/3
本卡只做：金币拍卖的挂单、成交、销毁税与流水。
不做：不新增货币；不把税记给任何账户；不让绑定物上架；不本地算税价。
允许改：db/trade/auction.sql、拍卖仓储与网关路由、客户端 Net 拆装件、check-p1-5a.sh。
冻结：
  - proto：已有 Auction 消息的字段编号与类型
  - RPC / 拒绝码：已有 reason 码；业务拒绝一律 HTTP 200 + ok=false
  - DB 列 / 约束 / 迁移版本：auction_settlement 的 CHECK (net_gold + tax_gold = price_gold)；auction_txn.txn_id 主键；auction_listing_live_slot 部分唯一索引；版本号只追加
  - config 键 / schema：config/auction.json 的税区间与取整方式
  - 网关路径：/auction/list、/auction/buy 的路径与回包字段
状态与拒绝码：listing 从 listed 到 sold / cancelled；同一 txn_id 第二次提交只回 duplicate，不二次扣发；余额不足、物品绑定、非本人挂单等拒绝时金币、元宝、背包一个字节都不动。
不变量：net_gold + tax_gold = price_gold；税没有收款方，全库金币净减少 tax_gold；元宝只是等量转移，全库总量不变；绑定物不在挂单里。
证据：
  - 静态：bash tools/check/check-p1-5a.sh
  - 真库：挂单 → 成交 → 只读口读回买卖双方余额与流水；拒绝路径跑一遍，余额不变
  - 变异：把 tax 记进卖方余额，期望 check 抓住
回滚点：挂单状态与流水都在库里；停掉成交入口即可，不删数据、不改表。
```

## 使用口径

1. 风险 `—` 的卡不填；填了也不增加审查深度。
2. 冻结面写到字段、键名、CHECK 名，不写「相关接口」「原有逻辑」这种模糊话。
3. 每个拒绝码旁边写清「哪些值必须是 0」；这是第 2 类和第 3 类的交叉点。
4. 证据必须是命令或可复现的场景，不写「已验证」。
5. 收口时按实际改动面复核风险标记；补标不回改历史，但要在日志里写一句「实际碰了第 N 类」。漏标不罚，漏审才是问题。
