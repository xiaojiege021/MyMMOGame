# 不变量清单

> D17 的交付物，供人工审查与收口复核用。**只回答一件事：库里现在有没有「规则上不可能出现、但代码或种子已经写进去」的行。**
>
> 一条不变量 = 一段只返回「违反行」的 `select`。干净库上**违反数必须为 0**；有行就要人判断是产品写入 bug、核对种子直写残留，还是迁移没跑。判定只读，不自动修。

## 怎么跑

```bash
# 无库段：文档 / 编号 / 只读入口 / 护栏（进 ci.sh）
bash tools/check/check-invariants.sh

# 真库段：只在 ubu 本机跑（要建临时库；远程 pg_hba 只放行 gamedb）
MMO_INVARIANTS_HAS_DB=1 bash tools/check/check-invariants.sh
```

真库段不碰现成的 `gamedb`：自己在同一个实例上建 `mmo_d17_inv_<pid>`、按 `db/migrations.json` 建全，先验 19 条 0 违反，再删一行 `schema_version` 造违反，验它被抓住（退出 **7**）且第二次跑仍红，最后 `drop database`。现成库里的测试残留不会被这个脚本改一个字。

ubu 现成的 `gamedb` 有两个限制：`pg_hba` 只放行 `gamedb` 给 `game_dev`，`game_dev` 也没有 `CREATEDB`，所以脚本自建库那一步会被挡。两条路：① `MMO_INVARIANTS_DB=<一次性库>`，库由人先建好；② 在 ubu 上起一个一次性 `postgres:17-alpine`（高位端口，如 `127.0.0.1:55432`），把 `MMO_GAMEDB` 指过去，跑完停容器——v1.182 用的是第 ② 条，脚本自建库 / 删库全程没碰服务器配置。

单独跑某一库：

```bash
# 与环境变量 / /srv/mmo/gamedb.env 里的连接串同一个库实例，--db 只换库名
dotnet tools/probe/CliProbe/bin/Release/net10.0/CliProbe.dll --db gamedb --invariants
```

**只读保证**：一笔 `repeatable read` 事务，先 `set transaction read only`，之后任何 `insert / update / delete` 都会被 Postgres 以 `25006` 拒绝。输出里的 `invariants_read_only=on` 是证据；核对器不自愈，违反修不修由人决定。

## 判定总表

| 编号 | 不变量 | 判定（SQL / 查询） | 为什么必须成立 | 违反时先看哪里 |
| --- | --- | --- | --- | --- |
| INV-01 | 货币非负 | `select count(*) from "角色".currency where amount < 0` | 余额只会被「带余额条件的扣减」改小；出现负数说明有一笔扣减绕过了 `amount + $ >= 0` 的条件，或旧数据带病。 | `CurrencyRepository` 的扣减语句；库层 `currency_amount_check` 是否还在 |
| INV-02 | 币种只在配置里 | `select count(*) from "角色".currency where kind not in (config/currency.json 的 id)`，另查 `"交易".stone_listing` 的 `stone_kind` 同一条 | 币种唯一正本是 `config/currency.json`（金币 / 灵石五档 / 元宝 / 家园币）。表外币种意味着代码里又开了一种货币，或把拍卖税记进了某个账户——「税没有收款方」正是靠这条守住。 | 写 `currency` 的 SQL 是否拼了字面 `kind`；`auction_settlement` 的税是否被记成收入 |
| INV-03 | 背包数量与格位 | `select count(*) from "角色".inventory where count <= 0 or slot < 1 or slot > bag_slots` | 一格一样东西，扣光要删行；格位上限是 `character.json` 的 `bag_slots`，库里允许到 200 只是防呆。超上限的行客户端看不到、卖不掉，却占着数据。 | `InventoryRepository` 的取空格与扣光即 `delete`；`bag_slots` 是否被下调过 |
| INV-04 | 绑定态与绑定时长同生同灭 | `select count(*) from "角色".inventory where bound <> (bound_at is not null)` | 解绑道具按 `bound_at` 算需要几张；只改 `bound` 不改 `bound_at`（或反过来）会让计价按空值 / 旧时间算，绑定物也能被当成未绑物流通。 | 购买到账绑定、拾取绑定、`UseUnbindItem` 三条路径；库层 `inventory_bound_at_matches` |
| INV-05 | 背包物品编号在物品表里 | `select count(*) from "角色".inventory where item_id not in (config/items.json 的编号)` | 物品编号只从配置来；表外编号是代码里写了字面编号，客户端没有图标、服务端没有堆叠上限与绑定规则。 | 发放 / 掉落 / 任务奖励的写入；配置里是否删过还在背包里的编号 |
| INV-06 | 绑定物不在挂单里 | `select count(*) from "交易".auction_listing l join "角色".inventory i on i.character_id = l.seller_id and i.slot = l.slot where l.state = 'listed' and i.bound` | 成交时物品进买方**未绑**格；绑定物能上架，绑定态就被洗掉了。挂单由全局服务写，成交却由角色服判，两个进程之间只有这一条检查。 | 全局服务的挂单入口；`AuctionRepository.SettleAsync` 的 `bound_item` 拒绝 |
| INV-07 | 挂单指向的货还在、数量够 | `select count(*) from "交易".auction_listing l left join "角色".inventory i on i.character_id = l.seller_id and i.slot = l.slot where l.state = 'listed' and (i.id is null or i.count < l.count)` | 挂单只引用「卖方 + 格位」，货没被冻结。货不在或不够时，成交要么到最后一刻才失败，要么卖出不存在的货。 | 挂单时的库存快照；成交第 3 步锁格与 `item_insufficient` |
| INV-08 | 物品拍卖成交守恒 | `select count(*) from "交易".auction_settlement where net_gold + tax_gold <> price_gold` | 买方付 `price`、卖方得 `net`、中间 `tax` 直接销毁。三者不等就是凭空造钱或吞钱，回档才能补。 | `auction_settlement` 的写入事务；库层 `CHECK (net_gold + tax_gold = price_gold)` |
| INV-09 | 元宝寄售成交守恒 | `select count(*) from "交易".auction_ingot_settlement where net_gold + tax_gold <> price_gold` | 与 INV-08 同一条规则，另一张表。元宝在买卖双方之间等量转移，金币只销毁税。 | `IngotRepository` 的成交事务；税率是否只来自 `config/auction.json` |
| INV-10 | 灵石拍卖成交守恒 | `select count(*) from "交易".stone_settlement where net_gold + tax_gold <> price_gold` | 与 INV-08 同一条规则，第三张表。灵石是货币行，不是背包行。 | `StoneAuctionRepository` 的成交事务 |
| INV-11 | 成交状态与流水一一对应 | `select count(*) from "交易".auction_listing l where l.state = 'sold' and not exists (select 1 from "交易".auction_settlement s where s.listing_id = l.listing_id)`，另查「有结算但挂单非 sold」「成交事务没有结算」各一条，三类拍卖都做一遍 | 挂单状态、成交事务号、结算流水必须同一笔事务提交。sold 无流水 = 成交没记账；有流水非 sold = 账实不符；txn 占号没结算 = 重复提交把号烧掉了。 | 三笔成交事务的提交顺序；`auction_txn` 抢号与 `Rollback` |
| INV-12 | 等级与经验范围 | `select count(*) from "角色".character where level < 1 or level > level_cap or exp < 0 or (level < level_cap and exp >= exp_per_level)` | `ExpTable.Apply` 在低于封顶时会把够一级的经验换成等级；低于封顶却留着 `exp >= exp_per_level`，说明有人绕过 `SettleExp` 直写了经验（核对种子就有一条这样的入口）。封顶后经验可继续累计、不夹取。 | `ExpSettlementRepository`（`exp` 唯一写入口）；`--raw-exp-write` 的核对种子 |
| INV-13 | 疲劳与周份额非负 | `select count(*) from "角色".character where fatigue < 0 or weekly_share < 0` | 疲劳按日归零、周份额按周归零，只会被进本结算加；负数说明日 / 周界或扣减写错。 | `DungeonEntryRepository` 的日界 / 周界；库层两条非负 CHECK |
| INV-14 | 经验流水不降级 | `select count(*) from "角色".exp_settlement where level_after < level_before` | 等级不会掉：复活卷轴只扣 `exp`、不写 `level`。流水里 `after < before` 说明有路径改了等级，升级曲线与回放都会对不上。 | `exp_settlement` 的写入方；卷轴 `Consume` 是否只写 `exp` |
| INV-15 | 迁移版本与清单一致 | 每个 schema 各 `select id from "角色".schema_version`（社交 / 交易同），与 `db/migrations.json` 的 id 集合比；缺、多、表不存在都算违反 | `schema_version` 是「这个库跑到第几版」的唯一事实。与清单不符说明迁移没跑、跑错 schema，或已应用的版本被手改；后面所有卡都以为库是新的。 | `--schema-status`；`tools/env/db-migrate.sh`；是不是只跑过 `--sql` 老路径 |
| INV-16 | 角色位范围 | `select count(*) from (select a.account from "角色".account a left join "角色".character c on c.account = a.account left join "角色".character_slot s on s.account = a.account group by a.account, s.slots having count(c.id) > coalesce(s.slots, base_slots)) t`，另查 `character_slot.slots` 不在 1–16 的行 | 名额由 `"角色".character_slot` 一行（没行按 `config/character_slot.json` 的 `base_slots`）说了算；多出来的角色只能是绕过购买建的。核对种子会用 `--raw-grant-character-slot` 造名额，所以现成开发库上这条常有测试残留。 | `CharacterSlotRepository` 的建号前判定；核对种子的 raw grant |
| INV-17 | 充值订单状态与时刻一致 | `select count(*) from "角色".recharge_order where (status = 'paid') <> (paid_at is not null)` | `paid` 必须有到账时刻，`pending` 必须没有；否则对账与退款分不清「到没到账」。 | `RechargeRepository` 的订单状态写入口；库层 `recharge_order_paid_at_matches` |
| INV-18 | 个人贡献等于任务流水之和 | `select concat('sect=',c.sect_id,' character=',c.character_id,' contribution=',c.contribution,' ledger=',coalesce(sum(l.contribution),0)) as detail from "社交".sect_contribution c left join "社交".sect_task_ledger l on l.sect_id=c.sect_id and l.character_id=c.character_id group by c.sect_id,c.character_id,c.contribution having c.contribution<>coalesce(sum(l.contribution),0) union all select concat('ledger-only sect=',l.sect_id,' character=',l.character_id) as detail from "社交".sect_task_ledger l where not exists (select 1 from "社交".sect_contribution c where c.sect_id=l.sect_id and c.character_id=l.character_id)` | 贡献与流水是同一笔事务写的：流水记这一笔加多少，贡献行记累计。两者不等说明有一边漏写，或有人绕过完成入口直写了贡献。 | `SectTaskRepository.CompleteAsync` 的写顺序；`sect_contribution` 是否被别的入口 UPDATE |
| INV-19 | 任务进度次数等于同周期流水条数 | `select concat('character=',p.character_id,' task=',p.task_id,' period=',p.period_key,' done=',p.done_count,' ledger=',count(l.txn_id)) as detail from "社交".sect_task_progress p left join "社交".sect_task_ledger l on l.character_id=p.character_id and l.task_id=p.task_id and l.period_key=p.period_key group by p.character_id,p.task_id,p.period_key,p.done_count having p.done_count<>count(l.txn_id) union all select concat('ledger-only character=',l.character_id,' task=',l.task_id,' period=',l.period_key) as detail from "社交".sect_task_ledger l where not exists (select 1 from "社交".sect_task_progress p where p.character_id=l.character_id and p.task_id=l.task_id and p.period_key=l.period_key)` | 完成一笔同时写进度 +1 与一行流水；次数上限、重置、面板都读进度，流水是审计。两者不等说明计数与账本分叉，重置或重放会算错。 | `SectTaskRepository.CompleteAsync` 的进度 UPSERT 与流水 INSERT 是否同一笔事务；`period_key` 是否来自同一个日历值 |
| INV-20 | 城池任务进度次数等于同周期完成笔数 | `select concat('character=',p.character_id,' task=',p.task_id,' period=',p.period_key,' done=',p.done_count,' ledger=',count(distinct l.txn_id)) as detail from "角色".city_task_progress p left join "角色".city_task_ledger l on l.character_id=p.character_id and l.task_id=p.task_id and l.period_key=p.period_key group by p.character_id,p.task_id,p.period_key,p.done_count having p.done_count<>count(distinct l.txn_id) union all select concat('ledger-only character=',l.character_id,' task=',l.task_id,' period=',l.period_key) as detail from "角色".city_task_ledger l where not exists (select 1 from "角色".city_task_progress p where p.character_id=l.character_id and p.task_id=l.task_id and p.period_key=l.period_key)` | 完成一笔同时写进度 +1 与这一笔的流水。一条任务可能有多行奖励（多个灵石档），所以数的是 `distinct txn_id` 不是行数；不等说明次数与账本分叉，重置或重放会算错。 | `CityTaskRepository.CompleteAsync` 的进度 UPDATE 与流水 INSERT 是否同一笔事务；`period_key` 是否来自同一个日历值 |
| INV-21 | 城池任务流水都走唯一发放入口 | `select concat('txn=',l.txn_id,' character=',l.character_id,' task=',l.task_id,' currency=',l.currency) as detail from "角色".city_task_ledger l where not exists (select 1 from "角色".grant_txn g where g.txn_id=l.txn_id)` | 灵石只从 `GrantRepository` 的货币写法发出去，同一笔事务先抢 `grant_txn` 号。账本里有号、`grant_txn` 里没有，说明有人绕开发放入口直写了货币行。 | `CityTaskRepository.CompleteAsync` 是否仍先 `TryClaimTxnInTransactionAsync`；有没有别的入口直接 UPSERT `"角色".currency` |

## 违反怎么处置

1. **先分类，再动手**：产品写入 bug（改代码 + 洗数据）/ 核对种子直写残留（核对入口本来就会绕过业务规则）/ 迁移没跑（跑 `tools/env/db-migrate.sh`）。前两类要开卡修，第三类只是操作。现成开发库上 INV-12 / INV-16 的测试残留很常见，别把它当产品 bug。
2. **不自动修**：判定只读，不给修复语句。修复要单独一张卡，写清事务边界与回滚点（14.11 第 2 类）。
3. **造违反验器**：真库段在临时库里删一行 `schema_version`，验核对器抓得住、退出 7、第二次跑仍红——证明它不是「跑完自己补好了」。
4. **语义逃逸回填**（14.11.5 第 4 条）：收口后才发现「当时全绿、规则错了」的，必须补一条不变量或一条变异登记，并在 `docs/不可逆点清单.md` 补锚点；只改代码不回填，下一次还会从同一个地方漏。

## 维护口径

- 编号只追加：新不变量从 **INV-22** 起，不改已有编号与含义；要改判定就改「判定」一栏，并同时改 `tools/probe/CliProbe/InvariantCli.cs`。
- 文档与探针两处必须一致：`check-invariants.sh` 无库段逐条比 id 集合，少一条、多一条、改名都红。
- 每条只判定**一个**语义；同一个号里塞两件事，红的时候看不出先修哪件。
- 本清单不替代 `check-*.sh` 的拒绝路径断言：拒绝时「数值一个字节不动」由各卡自己的脚本证明，这里只看落库后的终态。
