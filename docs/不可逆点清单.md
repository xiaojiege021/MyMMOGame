# 不可逆点清单

> 人工审查只花在这里：**改坏了修不回来的四类地方**。其余所有改动（命名、目录、日志文案、界面排版、注释、拆分与抽公共库）都由核对脚本与 CI 兜着，不看。
>
> 本清单是 D15 的交付物，配合 `tools/check/mutate.sh`（变异验证）用。派一张卡前查一次，收尾时再查一次。

## 为什么只审这四类

项目是单人 + AI 派工：91 张已派卡（本清单是第 92 张的交付物）、22.8 万行代码，每卡 diff 500–2200 行。**逐行读 diff 在这个量级上不成立**，人力和注意力都不够，读了也记不住。

能审过来的东西必须满足两个条件：**数量少**、**错了代价高**。全仓库只有四类同时满足：改错了要么数据洗不回来、要么钱对不上、要么客户端静默接受非法结果、要么两个进程各写一份。其余的地方错了，下一张卡或下一次 CI 就会红，让脚本去发现。

一条判据：**如果这处错了，能不能只改代码就修好？** 能 → 不进清单。不能（要洗库、回档、补数据、改客户端后才能纠正）→ 进清单。

## 四类总表

| # | 类别 | 错了会怎样 | 主要锚点 | 谁守着 |
| --- | --- | --- | --- | --- |
| 1 | schema 与迁移顺序 | 表建错、列改了、约束漏了，线上数据要洗 | `db/migrations.json`、`db/*/*.sql`、各 schema 的 `schema_version` | `check-d8.sh` |
| 2 | 钱的写入口与事务边界 | 金币 / 元宝 / 物品凭空多出或消失，只能回档 | `config/currency.json`、`auction.json`、`enhance.json`、`crystal.json`、`inventory` | `check-c7.sh`、各经济卡 |
| 3 | 协议拒绝码与 `ok=false` | 客户端把拒绝当成功，屏上显示假结果，玩家能做不该做的事 | 网关路由、各 RPC 的 `ok` / reason 码、未生效数值 | 各卡 check 的拒绝路径段 |
| 4 | 跨进程数值口径 | 两个进程各算一份，同一个数在两个地方不同 | 角色服 / 战斗服 / 世界服边界、`Shared.Domain` | `check-c6.sh`、各服 check |

## 1. schema 与迁移顺序

**判据**：本卡新增或修改了 `.sql`、`db/migrations.json`、`schema_version` 的读写、或任何 `CHECK` / `UNIQUE` / 外键。

**为什么不可逆**：库里已有的行不会因为你改 DDL 就跟着变。加一条 `CHECK (count > 0)` 而库里有 0 行，迁移当场失败；改列类型而数据有溢出，要么丢精度要么整表锁死。这类错误修起来不是改代码，是写数据修复脚本 + 停机窗口。

**15 分钟里只问三句**：

1. 这张新表，**空库从零建**和**老库补建**是不是同一条路径？两个都跑过吗？（只验过其中一个就是没验）
2. 新加的约束，**现有的行能不能满足**？谁扫过一遍？
3. 清单里的版本号是**追加**还是**插入**？插入到中间会让已应用的库变成 `drift`。

**锚点**：`db/migrations.json`（39 条，角色 23 → 社交 12 → 交易 4）、`db/character/character.sql`、`db/social/social.sql`、`db/trade/*.sql`、`tools/env/db-migrate.sh`。

## 2. 钱的写入口与事务边界

**判据**：本卡让任何数值（金币、元宝、灵石、物品数量、经验、税）**增加或减少**，或新增一条扣减 / 发放路径。

**为什么不可逆**：钱一旦写进库，日志只能证明「发生过」，不能证明「本该怎么发生」。回档要停服，补发要人工核对，多写一笔少写一笔都要一个个玩家对。

**15 分钟里只问三句**：

1. 这个数**只有一个写入口**吗？还是这张卡又开了一条新的 `UPDATE` / `INSERT`？（两个写入口 = 迟早不一致）
2. 扣减和发放是不是**同一条事务**？中间失败会不会只扣不发？
3. 拒绝路径**有没有真的写库**？失败时数值应该**一个字节都不动**，能不能用只读入口证明？

**锚点**：`config/currency.json`、`config/auction.json`、`config/enhance.json`、`config/crystal.json`；`db/trade/auction.sql` 的 `CHECK (net_gold + tax_gold = price_gold)`（**tax 没有收款方**，别给它加账户）；`inventory.count` 的 `CHECK (count > 0)` + 扣光即 `delete`；`src/Character/ExpSettlementRepository.cs`（`exp` 的唯一写入口，卷轴也只走它）；`src/Character/CityTaskRepository.cs`（Q5：灵石发放先抢 `grant_txn` 号 → 只走 `GrantRepository` 的货币写法 → 城池抽成只写 “社交”.city_stone_tax_ledger、**不从玩家扣**，与金币账本两张表）。

## 3. 协议拒绝码与 `ok=false`

**判据**：本卡新增或改动了网关路由、proto 字段、RPC 返回值、reason 码，或客户端读回包的判定。

**为什么不可逆**：这类错误不会让任何脚本变红——服务端「正确地」返回了一个拒绝，客户端「正确地」解析了它，只是把 `ok=false` 当成了成功。等到玩家把不该做的事做完，数据已经落库了。而且它只在真机连服时暴露，CI 永远看不见。

**15 分钟里只问三句**：

1. 业务拒绝是不是 **HTTP 200 + `ok=false`**？不要用 4xx / 5xx 表达业务拒绝。
2. 被拒绝时**未生效的数值是不是 0**？屏上不能显示「扣了 100 但没发货」这种半成品。
3. 客户端拿到 `ok=false` 时，**有没有一条明确的失败文案**，还是拼空串（会撞 NRE 或显示上一个成功结果）？

**锚点**：`src/Gateway/*.cs` 的路由与 `OwnsAsync` 归属校验、`txn_id` 生成；各 RPC 的 `ok` / `reason`；客户端 `Assets/Net/*Entry.cs` 的失败分支（必须显式给空串与 `Array.Empty`）；`src/Character/CraftRepository.cs` 的 `FinishAsync` 无活分支——D17 补跑 K3 时抓到：`for update` 的 reader 未关就 `RollbackAsync`，Npgsql 抛 `NpgsqlOperationInProgressException`，回 `db_error` 而不是业务拒绝 `no_craft`（D17 只登记；v1.183 非卡片记录已修：reader 先关、再回滚、再抛）。

## 4. 跨进程数值口径

**判据**：本卡让同一个数值在**两个进程**里各有一份，或新增了跨服 / 跨进程调用、`Shared.Domain` 里的共享模型。

**为什么不可逆**：两个进程各算一份，短时间内看不出问题；等它们分叉了，你无法判断哪一份是对的——因为两份都「有代码依据」。这类债发现得越晚越贵，最后只能挑一份为准、人工修数据。

**15 分钟里只问三句**：

1. 这个数**谁是唯一写入方**？（持久数据只有角色服；战斗服本地结算不回写；世界服只在内存）
2. 两个进程读的是**同一份表 / 同一份配置**，还是各自 `Load` 了一遍？（各自加载 = 两份正本）
3. 档位、概率、税率这类**判定**，是不是只在服务端算一次、客户端只翻译？

**锚点**：`src/Shared.Domain`（副本 / 掉落 / 世界 Boss 三张表一份）、角色服写入边界、世界服独立 gRPC 不连角色库、`FlightGate` / `RegionGate` 这类唯一判定点。

## 怎么用

**派工前**（读第 14 节完成标准时）：这张卡的判据命中哪一类？命中就在回复里写一句「本卡触碰第 N 类，收尾会核 X / Y / Z」。没命中就写「不触碰不可逆点」——写下来才知道自己漏没漏。

**收尾时**：只跑命中那几类的三个问句，不要通读实现。答不上来的，就是这张卡最该补的断言。

**每 5 张卡做一次变异验证**：

```bash
bash tools/check/mutate.sh --card d8     # 改坏一处实现，跑该卡 check，期望变红
bash tools/check/mutate.sh --all         # 所有已登记的卡
```

全绿的变异意味着**那条断言是空转的**：实现错了它也不会红。发现空转就补断言或登记为已知豁免，别放着——一条空转的断言比没有断言更危险，因为它给你假的信心。

## 和断言的关系

断言回答「**东西还在不在**」，变异验证回答「**断言还灵不灵**」。前者会随卡数增长而增长（现在 116 份脚本、3.9 万行），后者是一次性投入、每次只抽查几条。

两者都不能替代人工判断的地方就是这四类：断言能证明「字段名出现在文件里」，证明不了「这处该不该在这里写」。
