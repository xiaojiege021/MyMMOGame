# 数值台账

> C7 的交付物。所有可调数值只在 `config/` 与这张表各记一次；代码、proto、SQL 不留第二份。
> 改数值的顺序永远是：先改 `config/`，再改本表对应行的「现值」，然后重启读这份配置的服务。
> 本项目一人开发，「负责人」写的是这个数值将来归口的角色（数值 / 服务端 / 客户端 / 运维），
> 便于交接；当前全部由同一人承担，不再单独标在每一行。
> 这张表由 `tools/check/check-c7.sh` 核对：表 A 漏一份配置、表 B 的暂取项与配置对不上、
> 代码多出一个没登记的数值常量，都会红。

## 0. 怎么用

1. **要改一个数**：先在下面表 A 找到它属于哪份文件，确认「谁读」——那个服务重启才生效。
2. **这个数还没定**：表 B 里必须有它。方案补上数字之后，改指针为「方案写定」，并把配置里的
   `pending` 摘掉；两处必须同时改，否则核对脚本会报「表与配置不一致」。
3. **想往代码里塞一个数**：先看表 C。表 C 里没有的数值常量不许进代码；确实是规则常量（不是
   可调数值）的，登进表 C 并写明为什么它不是可调数值。
4. **想往 SQL 里塞一个数**：先看表 D。`db/` 里的 CHECK 只作最后一道闸，档位数只能来自 `config/`。

三条硬口径，与 `docs/开发架构.md` 第 14.7 节一致：

- 物品编号、价格、货币、发货方式、限购、配方、输入 / 产出、掉落、奖励只出现在 `config/`。
- 缺字段 / 越界就起不来，不给默认值兜底。代码里出现 `?? 数字` 读配置一律视为第二套数。
- 改配置重启生效；运行期不热更数值。

| `Character/MainlineTable.cs` | `StageCount` | 12 | 方案写定主线十二场 |
| `Character/AuctionTable.cs` | `WrittenMinRatePct` / `WrittenMaxRatePct` | 5 / 8 | 方案写定拍卖税率区间；配置只能落在这个区间 |
| `Character/HeroCodexTable.cs` | `EntryCount` / `MaxEntryPassiveBps` / `MaxTotalPassiveBpsCap` | 9 / 100 / 1000 | 方案 2.7 九位英灵；被动单条 1%、总和 10% |
| `Character/CharacterGrpcService.cs` | `MinLevel` / `MaxLevel` | 1 / 100 | 方案写定等级上限 100（与 `exp.json` 封顶一致） |
| `Battle/Server.cs` | `TickIntervalMs` | 50 | 结算节拍（20 Hz），是协议节拍不是玩法数值 |

这些常量的作用是**校验配置**（配置不等于写定值就起不来），不是参与计算。所以它们与
「数值只在配置里」不冲突：真正生效的值仍然来自 `config/`。

### 3.2 结构 / 协议常量：与玩法无关

### 3.3 校验边界：只拦不合理值

配置类里的最小值 / 最大值（如 `db_pool_max` 1–20、`bag_slots` 1–200、`fatigue_daily_cap`
1–1000000、`line_capacity` 1–10000、`duration 60` – `86400`）都是**范围校验**，作用是
「写错了就起不来」，不参与计算，也不是第二套数。这类数字不需要逐个登记，但**不许拿来给
缺失字段填默认值**（见 3.4）。

### 3.4 不许出现的东西：给配置填默认值

| 判据 | 现状 |
| --- | --- |
| `?? 数字` 直接给配置字段兜底 | 本卡前有 5 处（`bag_slots`、`fatigue_daily_cap`、三处 `db_pool_max`），已全部改成「缺字段就起不来」 |
| record 参数位上的默认数值（如 `int BagSlots = 40`） | 0 处 |
| 参与计算的算术魔数（系数、倍率、概率、时长） | 0 处；`check-c7.sh` 按白名单持续核 |

`??` 剩下的用法只有两种：给**非数值**字段兜空串（`?? ""`）和给结构体兜 `Array.Empty`。
这两种与数值无关。

## 4. 表 D：SQL CHECK（最后一道闸）

`db/character`、`db/trade`、`db/social` 共 **165 条** CHECK（按文件计；D8 把主迁移补全量后，同一份主迁移与分卡文件各有一份，**去重后是 134 条唯一约束**）。按作用分三类，全部只作最后一道闸：

| 类别 | 条数 | 例子 | 口径 |
| --- | --- | --- | --- |
| 数值范围 | 81 | `inventory.count > 0`、`currency.amount >= 0`、`tax_gold <= gross_gold` | 挡负数、零和越界。上界用「荒谬值」而不是方案现值：`fatigue <= 1000000`，不是 `<= 6000` |
| 枚举 / 状态 | 15 | `status in ('ok','rejected')`、`kind in (...)` | 挡写错的枚举串 |
| 相等 / 互斥 | 14 | `net_gold + tax_gold = price_gold`、`to_phase = from_phase + 1` | 一笔事务内部的自洽 |
| 非空 / 唯一 | 24 | `primary key`、`unique (character_id, slot)` | 结构约束 |

**为什么上界不写方案现值**：方案现值在 `config/`，改配置要重启才生效、但不该改库。库里钉
`6000`，那么把日上限调到 7000 时会被库反过来卡住——这就是「两处各记一个数」。本卡把唯一
一处这样写的地方（`character.sql` 的 `character_fatigue_daily_cap`）改成 `<= 1000000`，
与 `DungeonTable` 的校验范围对齐。

原则：**代码先拦，SQL 兜底**。任何一个数值如果只有 SQL 在拦、代码不拦，算「只有一道闸」，
属缺陷。审计结果：没有这种情形（数值型 CHECK 对应的字段都在代码里有前置校验）。

`realm_phase` 的 `0..8` 与 `to_phase = from_phase + 1` 看着像数值，其实是**结构**：段内阶
一共九档（索引 0–8），是方案 8.1 写定的阶数，不随配置变化。
