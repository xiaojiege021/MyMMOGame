## P0-1d · 2026-11-07

从前摇里打断这次施法没有伤害；进程崩掉重启，没写入的奖励不会冒出来。核对脚本 `tools/check-p0-1d.sh`，31 项全过。

- 打断这条路：客户端发出技能，160ms 后发取消（前摇 600ms），服务端回 `accepted=True`，10~18ms 就回了。再等 1 秒，队列里没有迟到的 `SkillResult`，伤害累计 0——撤掉的这次真的没打出去。
- 冷却退回：取消成功后同一技能立刻能再发，而且这一下命中（900→640）。撤掉那次占的冷却还回去了，没有白等一段。
- 已经结算完再发取消，回执是 `accepted=False`。这条是给界面用的：前摇动画播完那一刻要防手滑，撤不回来就别装作撤掉了。
- 打一半（900→380）直接 `kill -9`。重启后结算目录仍是 0 条，重进是满血 900/900，场次号也换了——崩之前那截进度没有任何地方被带回来。
- 打满四下通关，拿到事务号 `bt...`、经验 120，结算目录 1 条。再 `kill -9` 重启，仍是那 1 条，不补发、不重复；重进一场又是满血。
- **这一版没有背包**。完成标准里说的「背包没有这场未写入的奖励」，现在的落点就是结算记录：没通关一条都不写，通关只写一条，事务号唯一。等 P1-1 角色服做起来，这段换成角色库里的那一笔事务，事务号含义和幂等语义不变。
- 静态口径也进了脚本：结算写入全工程只有一处（`Encounter.Close`），断线走 `Abandon` 不写；客户端不碰结算、不算伤害。

没做的：安卓真机（P0-2a 起才上真机）、背包本身（P1-1）、掉线重连接着打同一场（这张卡的口径是「重连就是新一场」）。

踩到的坑：

- 异步方法不能带 `out` 参数（`CS1988`）。取收尾包那个辅助方法改成返回 `BattleEnded`，取不到回 `null`。
- `while (link.TryReceive(out var late))` 里的 `late` 会和后面同名局部变量撞（`CS0136`）。`out var` 的作用域是整个方法块，不是循环体。
- 脚本先把整行 `p01d_xxx=...` 的前缀剥掉再解析，遇到 `p01d_cancel_leak=0` 这种「前缀后面直接是值」的行，会把值一起剥掉，断言全挂成「没这行」。改成先按 `key=` 拆词找，找不到再取前缀后面那一段。

## P0-1c · 2026-11-07

客户端真的连上战斗进程了：本机 WebSocket 进来收开场包，把技能请求发出去，结果和拒绝原因都能收回来。核对脚本 `tools/check-p0-1c.sh`，33 项全过。

- 客户端收发层在 `client/MMOGame/Assets/Net`，独立程序集 `Mmo.Net`：引用 `Mmo.Proto`，不引用引擎。`BattleLink.cs` 只做四件事——连、拆信封、串行发、把收到的消息放进队列。命中判定、伤害、冷却一律不在这边算。
- **收包走异步循环，消息落 `ConcurrentQueue`，界面主线程自己取。** socket 线程上不碰 Unity 对象，省掉后面一类难查的崩溃。
- 网络属于基础设施，放在主包这侧；点选、前摇这些表现到 P0-2a 才进热更程序集。所以这一卡没有动 `Assets/HotUpdate`。
- 地址不写死。核对时脚本起进程、从 `listen=` 那行取实际端口，转成 `ws://` 再传给客户端；将来进本流程从配置里给。
- 客户端显示血量只认两个来源：`BattleOpened` 的双方血量、`SkillResult` 的 `target_hp_after`。它不自己扣血，也就没法和服务端算出两个数。
- 单包上限 64KB，和服务端同一个数，超过就断开——不把内存交给对面决定。
- 连不上给 2 秒超时再抛出来，不挂住界面。核对里拿 `127.0.0.1:1` 当反例，实测 39ms 就报错。

完成标准「请求能发出，结果能回到客户端」逐条对：

- 开场：`p01c_opened=session=... boss=9001 boss_hp=900/900 caster_hp=1200/1200 distance_mm=6000`，四个数和 `config/battle.json` 一致。
- 出手：`p01c_result=skill=1002 hit=True damage=260 hp_after=640 elapsed_ms=651`。从发出到收到 651ms，前摇 600ms 没有被跳过——结果确实是结算之后才回来的，不是本地先演一遍。
- 拒绝：`p01c_rejected=reason=SkillRejectCooldown retry_after_ms=613`。这一下是等后摇走完（700ms）、冷却还没好（2000ms）时发的，所以必然撞冷却。被拒之后又等了 300ms，`p01c_reject_leak=0`，没有迟到结算，血量也没再动。
- 收尾：客户端正常断开，服务端 `session_open` / `session_close` 各 1 条；Boss 没死，结算目录仍然是空的。

回归：`check-p0-1a.sh` 15 项、`check-p0-1b.sh` 31 项、`check-e8.sh` 7 项，都仍全过。

没做的：点选、切换目标、前摇表现和走位（P0-2a、P0-2b）；网关鉴权和进本资格（P1-1a2、P1-2）；Android 真机这一路——本机没有 adb 也没有设备，本卡按「手机或本机」里的**本机**验，真机留到 P0-3c 一起看。

踩到的坑：

- `using System.Diagnostics;` 和 `UnityEngine.Debug` 撞名，`Debug.Log` 直接编译不过。要 `using Debug = UnityEngine.Debug;`。
- 批量模式下主线程 `await` 会自己等自己：续体排回主线程，而主线程正卡在 `.GetAwaiter().GetResult()` 上。整个流程得包进 `Task.Run`，让它在没有同步上下文的线程上跑。
- 拒绝原因在 C# 里是 `SkillRejectCooldown`。proto 写的是 `SKILL_REJECT_COOLDOWN`，脚本第一次照着 proto 的名字断言，白挂一项。

## P0-1b · 2026-11-07

一个 .NET 战斗进程能打一场单人 Boss：本机 WebSocket 进来就是一场，一次只结算一个技能，冷却、距离、目标对不上都拒绝且不动目标生命，通关才写一条结算记录。核对脚本 `tools/check-p0-1b.sh`，31 项全过。

- 协议加在 `proto/mmo/battle.proto`：拒绝原因枚举、`SkillRejected`（带 `retry_after_ms`）、`SkillCancelRequest` / `SkillCancelled`、`BattleOpened`、`BattleEnded`，以及 `ClientMessage` / `ServerMessage` 两个信封。一条连接上跑多种消息，总得有个信封分辨。`SkillResult` 补了 `target_hp_after`，客户端照着改血条，不自己算。
- 战斗进程在 `src/Battle`：`Config.cs` 读配置、`Encounter.cs` 是这一场的状态机、`Settlement.cs` 写结算、`Server.cs` 是 Kestrel 起的 WebSocket 入口。`Battle.csproj` 加了 `Microsoft.AspNetCore.App` 和 `Shared` 的引用。
- **结算发生在前摇之后，不是收到请求就结算。** 收到请求立刻结算的话，「打断后这次施法没有伤害」就做不到了，客户端停掉的只是本地动画，服务端那一下已经打出去了。现在是：接受施法 → 占住冷却 → tick 到 `foreswing` 末尾才结算 → 发 `SkillResult`。取消在结算之前到达就把这次撤掉。
- **冷却从出手时算，不从结算时算。** 从结算算，延迟高的人反而多一截冷却外的空窗，等于给慢网络让利。取消时把冷却退回出手前的值，技能没放出去就不该占冷却。
- **拒绝的顺序**：场次结束 → 技能编号不认识 → 目标编号对不上本场的 Boss → 前摇中（`CASTING`）→ 后摇中（`RECOVERY`）→ 冷却 → 距离。前摇排在冷却前面，因为「一次只结算一个」是更硬的约束，同一技能在前摇里本来也还在冷却中。
- 后摇按技术架构写的「不取消后摇」实现了：结算后 `recovery_ms` 内发技能一律 `RECOVERY`。这三个拒绝原因分开，核对时才能分别证明。
- **Boss 这一版不反击。** 玩家在本卡不会掉血，所以 `CASTER_DEAD` 只在协议里留着，代码里没有分支。Boss 的阶段和读招在 P0-3。伤害取配置里的固定值，不接主属性——力量、敏捷、精神在 P0-3 才进公式。
- **结算先落本地目录** `var/battle/settlements/`，一场一条，文件名就是事务号 `bt{session:016x}`。写的时候先写 `.tmp`、刷盘、再 rename，中途挂掉只留一个临时文件，不会出现半条记录。同一个事务号再写一次直接返回，不重复发奖。等 P1-1 的角色服做起来，整条换成那一笔事务，事务号和幂等语义不变。
- 写不下就不发号：`BattleEnded` 的 `settlement_id` 交空、经验给 0，客户端拿不到号就领不了奖，进程自己也记一行 `settlement_error=`。宁可这次没有，也不发一个查不到的号。
- 配置全在 `config/`：`battle.json`（监听、双方血量、站位、结算目录）和 `skills.json`（三个技能）。启动时校验：编号唯一、数值非负、前摇必须大于 0（前摇为零就没有取消窗口）、至少有一个技能够得着站位（否则这场打不完）。
- 站位是 6000mm，近战技能 range 3000，正好用来看「距离不够」的拒绝。这一版没有移动协议，站位固定，等 P0-2 的走位接进来。

核对按 P0-1 的三条完成标准逐条对：

- 完成标准一「连续两个还在冷却中的技能，只有第一次生效」：`case=cooldown first_damage=260 second_reason=SkillRejectCooldown retry_after_ms=648`。
- 完成标准二「打断后这次施法没有伤害」：`case=cancel accepted=True late_message=none hp_before=900 again_damage=260`。取消后等了 1.5 秒确认没有迟到的结算，紧接着再发一次能成功，说明冷却确实退回去了。
- 完成标准三「重启后这场没有写入的奖励不会出现」：通关写 1 条 → 重启后仍是 1 条、新开一场满血；再打掉一截血后 `kill -9`，重启后记录还是 1 条、新一场仍是满血；结算目录改成不可写再通关，`settlement_id= exp_gain=0`。

另外核了：开场满血、伤害与剩余血量对得上、前摇中再发被 `CASTING` 挡、后摇中再发被 `RECOVERY` 挡、编的技能号 `UNKNOWN_SKILL`、对不上的目标号 `TARGET_GONE`、这几种拒绝之后都没有迟到的结算且血量不动、通关后再发 `NOT_IN_BATTLE`。

回归：`tools/check-p0-1a.sh` 15 项仍全过（客户端字段清单多了 `target_hp_after`，两端一致），`tools/check-e8.sh` 7 项仍全过。

没做的（属于后面的卡）：客户端那侧的会话、点选和前摇（P0-2）；五个职业的技能表和主属性、蓝量、Boss 阶段（P0-3）；进本资格和人数缩放（P1-2）；进角色库的那笔事务（P1-1）；网关鉴权和协议加密。

踩到的坑：`SkillResult` 加了字段以后，`tools/check-p0-1b.sh` 里那条「P0-1a 字段还在」的断言一开始写成 glob 串匹配，`stagger_ms` 在 proto 里是 `uint32` 而不是 `int64`，串就断在那儿；改成逐条 `grep` 加字段类型一起对。另外通关场景里 `SkillResult` 和 `BattleEnded` 是两条独立消息，第一版循环只读一条就去发下一个技能，正好撞上 `NOT_IN_BATTLE`，改成打到 0 血时当场往下读一条。

### 本机复核（Windows）

拉到 `b1138aa` 后在本机跑 `tools/check-p0-1b.sh`，**首轮 29 项过、2 项未过**，两项都在第 11 段「写不下就不发号」。查下来是脚本的问题，不是产品的：

- `chmod 500` 改的是 POSIX 权限位，NTFS 不认。实测在 `chmod 500` 的目录里照样能建文件，所以「不可写」这个现场根本没造出来，服务端合法地写了记录、发了号，两项必假失败。
- 换成 ACL 复现才知道这里有两层坑：`icacls` 的 `/deny` 在 Git Bash 里会被 MSYS 当路径转换（报「无效参数 deny」），要加 `MSYS_NO_PATHCONV=1`；账户名 `xiaojiege021:(W)` 解析不到（ACL 里落成 `xiaojiege021\:`），用 SID `*S-1-1-0` 才稳。
- **不能连列目录一起拒**。只拒 `W` 的时候，战斗服启动时 `SettlementStore.Count()` 枚举目录直接抛 `UnauthorizedAccessException`，进程起不来，根本走不到写那一步。所以只拒 `WD`（建文件）和 `AD`（建子目录），保留 `RD`。

用「能列、不能建」的目录手工跑了一次通关，确认降级是对的：`settlement_id= exp_gain=0`，日志 `settlement_error=session=... ...json.tmp is denied.`。脚本改完后重跑：**31 项通过，0 项未通过，退出码 0**，提交 `f6eba85`。

拉到 `15df5e1` 之后在 Mac 上又重跑了一遍，`make_unwritable` 走的是 `chmod` 分支，结果同样是 **31 项通过**——同一个脚本两边行为一致，这次改动没有把 macOS 弄坏。

修完留了两个东西：造不出不可写目录时打一行注意，不静默假通过；`cleanup` 里反过来解除 ACL，不然临时目录删不掉。

**另外记一个产品侧的问题，这一版没改**：`BattleProcess.RunAsync` 的 `CreateDirectory`（第 20 行）和 `Count()`（第 24 行）都在 try 之外。结算目录不可用时，整个战斗进程**启动即崩**，而不是降级成「不发号」——`Encounter.Close` 的 catch 只覆盖运行期写失败。启动时是该快速失败还是也降级，等 P1-1 把这条挪进角色库事务时一起定。
